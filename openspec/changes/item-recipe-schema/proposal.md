# Proposal: Item Recipe Schema + Icons

## Why

Three of the ten remaining roadmap features — Gestión de Materiales,
Validación y almacenamiento de recetas, and Calculadora de crafteo — all
need the same two things the `Item` catalog does not have today: a
machine-checkable recipe (what 9 grid slots produce this item, and how
many of each raw ingredient that implies) and a way to show the player an
actual Minecraft icon instead of a bare name. Building any of those three
features first requires this shared foundation to exist.

The team's Node reference prototype (`proyecto-node`) already solved both
problems: `full_id` (e.g. `minecraft:red_bed`) doubles as the key for a
public icon API (`https://blocksitems.com/api/v1/items/{full_id}/icon`),
and recipes are stored as a 9-slot `receta_matriz` plus a derived
`ingredientes_para_calculo` list, referencing other items by a
human-readable slug id (e.g. `lana`, `tablones_de_roble`) instead of an
opaque database id.

## What Changes

- **`Item` gains three fields**: `fullId` (optional, the Minecraft
  namespaced id used for the icon API), `recetaMatriz` (optional list of
  exactly 9 entries, each an item id or `null`, representing the 3x3
  crafting grid), and `ingredientesParaCalculo` (a list of
  `{itemId, cantidad}`, computed by the server from `recetaMatriz` —
  never accepted from the client — so the two never drift out of sync).
- **Item ids become slugs, not opaque Firestore ids**: on creation, an
  item's Firestore document id is derived from its `nombre` (lowercase,
  accents stripped, spaces to underscores — the same algorithm
  `proyecto-node`'s `scripts/seed-items.js` uses), instead of a
  Firestore-autogenerated string. The id does not change if `nombre` is
  edited later, since other items' recipes may already reference it.
- **Recipe shape validation**: `recetaMatriz`, if present, must have
  exactly 9 entries; it must be empty when `esMateriaPrima = true` (a raw
  material has no recipe). Creating an item whose derived slug id already
  exists is rejected instead of silently overwriting the existing item.
- **Web + REST forms** gain a `fullId` text field and 9 recipe-slot text
  inputs (plain text referencing another item's id; no drag-and-drop yet).
- **Item listing templates** render an `<img>` pointing at
  `blocksitems.com` using `fullId`, with a fallback if the API doesn't
  recognize the id.
- **Icon suggestions on create/edit**: a new endpoint translates the
  Spanish `nombre` into English via a small curated dictionary (the
  project's item vocabulary is a fixed, known set — no translation API
  needed), searches `blocksitems.com`'s item list, and returns up to 5
  ranked candidates. The create/edit form gains a "Sugerir ícono" button
  that fetches these candidates and lets the admin click one to fill
  `fullId` — the **first JavaScript in this project**, justified because
  the future Grilla 3x3 and Modelo 3D features will need JS regardless.

## Non-Goals

- **Grilla 3x3** (drag-and-drop crafting grid UI) — this only adds plain
  text inputs for the 9 slots; the interactive grid is its own future
  spec.
- **Deep recipe validation** (do all referenced ingredient ids actually
  exist in the catalog? circular dependencies?) — this proposal only
  validates the *shape* of `recetaMatriz` (size, materia-prima gating).
  Referential validation is explicitly the scope of the future
  "Validación y almacenamiento de recetas" feature.
- **Calculadora de crafteo** (aggregating raw materials needed for a
  build) — a future feature that will consume `ingredientesParaCalculo`,
  not part of this change.
- **Migrating existing Firestore item documents** to slug-based ids —
  only newly created items get a slug id; documents created before this
  change keep their existing autogenerated id and simply have no value
  for the three new fields (handled the same way this project already
  handles Firestore documents missing newer fields).
- **Introducing any client-side JavaScript framework** — the icon
  suggestion widget is a small vanilla-JS `fetch` + DOM update, not a
  framework; the grid inputs and icon `<img>` remain plain HTML/Thymeleaf.
- **A general-purpose Spanish↔English translation capability** — the
  dictionary only needs to cover this project's known item vocabulary,
  not arbitrary text.

## Rollback Plan

Additive only: three new optional `Item` fields, one new validation path,
one changed id-generation strategy for *new* items. A plain `git revert`
undoes it; no data migration is needed in either direction since existing
Firestore documents remain valid without the new fields.

## Impact

- Code: `Item.java` (new fields), new `Ingrediente` nested/record type,
  new `Slugs` utility, `ItemService.java` (slug-based id generation on
  create, duplicate-id rejection, recipe shape validation, server-side
  `ingredientesParaCalculo` computation), `ItemController`/
  `WebItemController` (accept new fields, surface validation errors),
  `items.html`/`item-edit.html` (fullId input, 9 recipe-slot inputs, icon
  `<img>`, "Sugerir ícono" button + JS), new `MinecraftEsEn` dictionary
  utility, new `IconSuggestionService` (calls `blocksitems.com` via
  `RestTemplate`, same pattern as `FirebaseIdentityService`), new
  `GET /api/items/sugerencias-icono` endpoint, new
  `src/main/resources/static/item-icon-suggest.js`.
- Tests: `Slugs` unit tests, `ItemService` tests (id derivation, duplicate
  rejection, recipe validation, ingredient computation), controller tests
  for the new validation error paths, `MinecraftEsEn`/`IconSuggestionService`
  tests (translation, ranking, namespace prioritization, empty-result
  fallback).
- No new dependencies (uses the existing `RestTemplate`, already a
  transitive dependency via `spring-boot-starter-webmvc`).
